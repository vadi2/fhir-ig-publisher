IG dependency checks (core ImplementationGuideValidator.checkDependency):
  The IG has three dependsOn: hl7.terminology.r5, fhir.dicom and hl7.fhir.uv.extensions.r5. For each one, every
  rebuild calls pcm.getPackageId, getPackageUrl, PackageClient.getVersions and getLatestVersion, each time with a
  NEW user-cache FilesystemPackageCacheManager. That new manager has a fresh CIBuildClient, which downloads the
  build.fhir.org ig list again.
  JFR main thread, prof build: packages2.fhir.org 1.75 s (32 reads) + packages.fhir.org 0.13 s (12) +
  CIBuildClient.updateFromCIServer 0.97 s + 0.13 s park = ~3.0 s.
  inst build: 1.53 + 0.10 + 1.03 + 0.13 = ~2.8 s.
  The tail is much worse than the median: one base-timed inst rebuild spent 27.8 s in this phase on a registry
  stall.

tx requests in a warm rebuild:

  - prof: 3 requests. The extra one is CodeSystem/$validate-code for the unknown system
    http://example.org/fhir/CodeSystem/lab-report-type (0.13 s). #2847's unknown-system memo lives in the per-build

  - No $expand in warm rebuilds. A first build on the seed cache makes 46 $expand calls: that is the

Which resources get re-validated, and is the set minimal?
  inst edit (Observation/blood-pressure-example): 4 validations:
    - the instance itself;
    - Bundle/example-transaction-bundle and Bundle/example-transaction-response;
    - the IG resource.
    This is minimal, apart from the IG resource, which is always dirty.
  prof edit (UZCoreSpecimen ^short): 90 validations. This is not minimal.
    - The closure follows every IG string transitively, including Reference.reference in instances and
      ElementDefinition.type.targetProfile. That pulls in the SDs that merely target Specimen (Observation,
      DiagnosticReport, ServiceRequest, Group, ...), then every example of those SDs, and so on.
    - Validating a reference needs the target to exist with the right type and nothing more.
      ValidationServices.policyForReference returns CHECK_EXISTS_AND_TYPE, or CHECK_TYPE_IF_EXISTS in Bundles.
      The exception is a resolve() or conformsTo() in a constraint or discriminator of the profile being used.
    - Measured with the weak-edge prototype: 27 validations (closure.py offline says 26 + the SD itself; the
      publisher agrees with closure.py's current rule on all 718 files).
    - Dropped: 64 validations worth 1.3 s in base (19 SDs, 7 ServiceRequest, 6 Condition, 5 Task, ...).
    - Kept: 6 profiles have resolve()/conformsTo in their snapshot (diagnostic-report, encounter, observation,
      procedure, provenance, socioeconomic-observation), so the safety rule keeps them and their examples.

Parallel validation: after ideas 1-3, a prof rebuild has about 0.9 s of non-IG validation CPU left (an inst rebuild
has about 0.1 s). Running it on several threads would save under 0.6 s. It is not worth the risk: InstanceValidator
state (setExample, fetcher flags), the order of statusWarnings and the Rapido record order all assume one thread.

2. RANKED IDEAS
==========================================================================================================
Seconds are per watch rebuild, from the ab1 A/B sessions (medians) unless marked EST.

1. Memoise the package-registry answers used by ImplementationGuideValidator   CORE   (prototype f392d67d14)
   What: one static user-cache pcm instead of a new FilesystemPackageCacheManager per dependency. Cache "id|uri",
     "url|pkg", "versions|pkg" (empty answers are not cached) and "latest|pkg" in a static map with a 1 h TTL,
     shared across the watch session's rebuilds.
   Saved: Validating Conformance Resources prof 4.9-6.2 -> 1.41-1.48 s and inst 4.4-5.0 -> 0.98-1.00 s. IG resource
     validation 3.2-4.9 s -> 0.72-0.97 s. Net -3.1 to -3.9 s on every non-page rebuild, and it removes the network
     tail (the 27.8 s stall seen once). This line also includes idea 2's share for prof (about 1 s).
   Risk: low. The messages depend only on registry state; a new version published mid-session shows up within the
     TTL. Message text unchanged: QA identical. An alternative with no TTL question is to skip the network checks
     when the IG's dependsOn list is unchanged since the last build of the session (publisher side).
   Effort: small (about 50 lines). Overlap: E (network in rebuilds), A (pcm construction).

2. Weak edges in the Rapido validation hash                                     PUBLISHER (prototype b0a8f677)
   What: in RapidoDependencyAnalyser, the validation hash follows only "strong" edges transitively:
     - profile claims (meta.profile, found profiles, exampleUri/test claims);
     - baseDefinition, bindings, type.profile, and all other strings.
   For "weak" edges, the hash includes only the target's identity: key, file, url, version, and type for SDs.
   The weak edges are:
     - Reference.reference in instances;
     - ElementDefinition.type.targetProfile;
     - xhtml narrative text.
   Safety rule: if the resource itself or anything on its strong closure has resolve() or conformsTo( in an
   expression/path/xpath (snapshot included), the full hash is used. The render hash still uses the full closure,
   so the render set is unchanged.
   Saved: prof re-validations 90 -> 27; the 64 dropped validations cost 1.3 s in base. Measured effect inside the
     Conformance and Validating Resources phases: about -1.0 to -1.3 s (it can't be separated exactly from idea 1 in
     the same jar). inst is unchanged (already minimal). The gain grows with IG size: one profile edit re-validates
     every example of every profile that targets it.
   Risk: medium-low. What could break: a validator check that reads target content outside
     resolve()/conformsTo(), or another policy than CHECK_EXISTS_AND_TYPE for some paths. Examples are
     CHECK_VALID for contained resources (those are inside the same resource) and Bundle entries (same file).
     The edge list should be reviewed against InstanceValidator.checkReference. Evidence: QA output identical to
     base for prof1, prof2, inst, restore-inst and the first build (qa.txt diff after removing timestamps).
   Effort: medium (about 140 lines including the scan changes, plus tests in PublisherRapidoWatchTest).

3. Count extension usages in one walk                                           PUBLISHER (prototype 775e09e2)
   What: validateSD -> countUsages(url) walked every element of every resource once per extension SD. Replace it
     with one walk that builds url -> count, rebuilt at the start of the validateSD loop.
   Saved: the "reused N of M" phase 0.85-0.91 -> 0.07-0.09 s, so -0.8 s per rebuild of any kind (and on the first
     build too). It grows as extensions x elements.
   Risk: none; same counts by construction. QA identical. Effort: trivial.

4. Keep the IG resource's validation when nothing it depends on changed         PUBLISHER   EST 0.7-1.0 s
   What: the IG resource is in alwaysDirty, so it is validated every rebuild. After idea 1 it still costs
     0.72-0.97 s CPU. If the IG element hash, the dependsOn list and the set of IG files are unchanged, its messages
     can be replayed like any other reused validation.
   Risk: medium. IG validation looks at the whole resource inventory, so its key must include that inventory (it
     changes when files are added or removed). Effort: small-medium.

5. Reuse the TerminologyCache between watch rebuilds                            CORE + PUBLISHER   EST 0.75 s
   What: each rebuild builds a new context, and TerminologyCache.load re-parses every entry (0.74-0.80 s CPU). Hand
     the NamedCaches to the next build's cache when each file's nonce/length on disk is unchanged (the nonce
     machinery already exists). Also keep #2847's unknown-system memo across rebuilds (saves the prof $validate-code,
     0.13 s).
   Risk: low if keyed on the disk nonce. Effort: medium (lifecycle across PublisherFields). Overlap: A (context
     loading), E.

6. Keep the terminology client across rebuilds                                  CORE + PUBLISHER   EST 0.27 s
   What: skip GET /metadata and $cache-control?mode=start when reconnecting to the same server inside a watch
     session. Risk: low (the capabilities are already cached on disk with a TTL). Small gain.

7. Cheaper expand-cache keys (definitionDigest)                                 CORE (prototype a5e7145105)
   What: JFR shows 1.1-2.7 s CPU per rebuild in generateExpandToken -> definitionDigest (composeString of the VS
     essence plus every dependency CS essence, for each expandVS call). That cost was added by #2856. The prototype
     memoises the essence JSON per resource object, guarded by a cheap stamp, for one build.
   Measured: render phases only 0.3-0.5 s faster (inside noise), so the identity key probably misses. expandVS
     often gets copies of the ValueSet, so each call brings a new object. A content-keyed memo, or a digest stored
     on the CanonicalResource when it is loaded, is needed to get the JFR number. Not proven; the time is in C's
     phases (narratives, HTML), so it overlaps C. Risk: medium (stale key = wrong expansion reused).

8. Parallel per-resource validation                                             PUBLISHER   EST < 0.6 s
   Not recommended for watch rebuilds after ideas 1-3 (see section 1). For the first build (16.5 s of validation)
   it may pay off, but that is E's area.

  - The "Errors: ... Broken Links" phase (D) was 1.5-4.5 s shorter in the proto session's prof rebuilds. That is not
    explained by these prototypes, so I treat it as noise.
  - The first-build comparison in ab1 is confounded: base ran first and filled the txcache (46 $expand calls);
