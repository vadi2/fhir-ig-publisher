Date churn (root cause of most "changed" bytes): PublisherIGLoader.java:4977 stamps pf.getExecTime() as `date` on
every canonical with no date. In DHP that includes the specimen, condition, observation SDs and many CodeSystems
and ValueSets. 515 of 718 en/*.json native files differ between two consecutive builds only by it. It also defeats
any byte-level reuse key (my first expansions key never matched because of it). RapidoTracker already hashes
the stamped date as "(build date)" and keeps the day in the global key (RapidoTracker.java:627). That is why the
first build after midnight is a complete build by design. D found the Jekyll side of the watch failure that
follows (D report section 4). The same date problem is why D's tail can't become incremental.

Threads (question 4): narratives, native, html, sheets and summaries all run on the main thread (0.7-0.85 cores
in JFR). Native outputs parallelise cleanly (prototype: 10.1 -> 4.2 s, output equal apart from dates). Parallel
html per file or per language would need per-thread copies of pf.expansions, trackedFragments, otherFilesRun,
the npm adders, the db and R2-style counters. It is a big refactor (estimate only). The post-Jekyll zips (10-12 s)
run while nothing else does, and they do not need Jekyll's output (idea 3).

Write time and #1458 staging (question 5): checkMakeFile compares before writing and is cheap: first build 71,208
html-phase writes (1.76 GB) took 1.03 s, a prof rebuild 14,532 writes (0.44 GB) 0.15 s. Writing is not where the
time goes; generating the bytes is. My runs are one-shot, so no .watch-output staging happens and I could not see
duplicate writes from #1458. D measured the sync: it writes 12,486 and byte-compares 8,212 files per FSH build.
Most of those writes are date churn.

2. RANKED IDEAS
----------------------------------------------------------------------------------
Seconds are per differential rebuild (prof / inst) unless noted. "measured" = A/B in part 3, "est" = derived
from phase timings, not built.

1. Render hash with weak edges (identity only for targetProfile / Reference / narrative links)    PUBLISHER
   What: the same strong/weak split B prototyped for the validation hash (B idea 2), applied to the render
     closure. A file is re-rendered when it changed, or something on its strong closure changed, or the identity
     (key, url, version, name, title, web path, type) of a weak target changed. "Render only" users
     (something that refers to it changed) are keyed the same way, on the identity of the referrer.
   Saved: prof ~-9 to -10 s html + sheets (est from measured per-file times: 10.1 of 11.0 s of re-rendered work had
     no real output change); inst ~-1 to -2 s (the 3 SDs among the render-only users are 1.1 s). Grows with IG size.
   Risk: medium. Renderers that read deeper into a referenced profile would go stale: obligations, "uses"
     lists, inherited must-support, tooltips. Mitigation: same resolve()/conformsTo() safety rule as B, plus an
     A/B check that the output equals a complete build on a few edit kinds (my analyze.py/ov.py do this).
   Effort: medium (RapidoDependencyAnalyser/RapidoTracker; B's code can be shared). Overlap: B, #1447.

2. Stable build time inside a rapido session                                                       PUBLISHER
   What: in a differential build, stamp the date, genDate and lastUpdated from the build that produced the state
     (stored in state.json) instead of now. The day is already in the global key, so the value is always from
     the same day.
   Saved: 0 s by itself. It makes 515 native json files, ~518 package entries, every expansion, the dated SD
     headers and (D) all ~8,900 html footers byte-stable. Without it ideas 4, 6 and 8 need date-blind keys, and D's
     incremental tail cannot work.
   Risk: low. Pages show the session's first build time; "same as a complete build apart from timestamps" holds.
   Effort: small. Overlap: D (genDate), E.

3. Run generateZips while Jekyll runs                                                              PUBLISHER
   What: generateZips (examples/definitions zips, expansions.json/.xml + zips, validator.pack and its copy,
     csv/excel/sch zips) reads only resources and the spec file, not Jekyll's output. Build the spec file before
     Jekyll, run generateZips on a worker thread while Jekyll runs, write to a staging folder and move the files
     into output/ after Jekyll (Jekyll may clean its destination). package.tgz and the combined package have to
     stay after Jekyll: templateOnCheck (after Jekyll) adds messages that go into validation-summary.json and
     validation-oo.json inside package.tgz, and the combined package is made from package.tgz.
   Saved: est -10 to -12 s every build, first build included (generateZips is 10.3-11.9 s, and Jekyll leaves the
     JVM idle for 25 s). Moving the template check earlier would add the 4.7 s package step, but the check
     may read the output.
   Risk: medium-low. Output bytes are unchanged. A failed Jekyll has to discard the staged files. The worker
     needs the context read-only (validator.pack composes resources). Effort: medium. Overlap: D (package step).

4. Expansions: reuse the files when no expansion changed, and don't parse journal expansions     PUBLISHER
   What: -Dr2c.expreuse. Replay keeps journal expansions as strings. generateExpansions hashes them (skipping
     date/timestamp/identifier values, proto4) and keeps expansions.json/.xml/.zips when the key matches.
   Saved: measured -1.4 s in the html loop (replay overhead 2.8 -> 1.4 s). The write skip is est -7 s per rebuild
     with no expansion change (prof and inst both): C spends ~7.4 s writing them, and proto4's check should cost
     well under 1 s (one pass over ~120 MB of chars, est). Not measured in a build: proto3's SHA-256 key never
     matched (the date problem) and its check cost 1.4-1.5 s. proto4's date-blind 2x64-bit key passed a unit check
     (a date/timestamp/identifier-only change gives the same key, a code change or a display "date" doesn't).
     Its p4 build sequence waited ~1 h for bench.lock and never ran, so I cancelled it.
   Risk: low-medium. The kept file has the older dates for re-rendered ValueSets, as html replay already does.
     With idea 2 the key would not need to skip anything.
   Effort: small (done as a prototype). Further, upstream question: expansions.json repeats each ValueSet once per
     language pass (null/en/ru/uz copies, same fullUrl). One copy per ValueSet would cut it to a quarter
     (est -5 s of the 7.4 s on every build). That changes the output, so it needs Grahame's call.

5. Native outputs on a thread pool                                                                 PUBLISHER
   What: -Dr2c.nativepar=10: generateNativeOutputs for all files on N threads, db rows and npm adds in file order.
   Saved: measured -5.9 s per rebuild (native 10.1 -> 4.2 s prof, 10.0 -> 4.1 s inst), -6.5 s first build.
   Risk: medium-low. Output check: all 780 package.tgz entries equal a C complete build after blanking dates
     (the one missing entry, openapi.json, comes from idea 7 or 10). Shared caches in the element model /
     context must be thread-safe; the 5 P builds ran clean. Effort: small-medium.

6. Replay narratives and native outputs for clean files                                           PUBLISHER
   What: files whose strong closure is clean (validation-clean) keep last build's narrative and native outputs
     (journal the generated text divs, or skip the native write when the content hash is unchanged).
   Saved: est -14 s sequential (narratives 5.3-5.9 s + native 8.6-9.3 s on clean files), or about -9 s on top of
     idea 5. Includes convertToElement (3.7 s of the narrative phase).
   Risk: medium-high. Narratives feed validation, db rows, npm entries and the combined package. Needs idea 2,
     or stale dates in native files. Effort: large.

7. Skip the null-language html pass (newML)                                                       PUBLISHER
   What: -Dr2c.nonull: the null pass only writes the unsuffixed redirects.
   Saved: measured -2.4 s prof, -0.75 s inst, -18.5 s first build (null pass 22.3 -> 3.8 s).
   Risk: HIGH as prototyped. P builds lose output/DHPCapabilityStatement.openapi.json and its package.tgz entry
     (6 broken links). openapi is only registered when lang == null, and prune (idea 10) doesn't whitelist it
     either; I did not separate the two. It removes the null copy from expansions.json, and the
     unsuffixed fragments change. A product decision; it needs the openapi registration moved to the default
     language pass. Effort: small once agreed.

8. Reuse summaries and Cross fragments in differential builds                                     PUBLISHER
   What: key generateSummaryOutputsAfter (3.3 s, 0 of 15,234 writes changed) and the dependency/globals/ip
     fragments (2.5 s) on a hash of the summary inputs (identity of all resources + lang), and cache
     package-list.json per day.
   Saved: est -3 to -5 s per one-shot rebuild (less in -watch if the package lists stay in memory).
   Risk: low-medium (the summary input set must be complete). Effort: medium.

9. Memoise TerminologyCache.definitionDigest per ValueSet                                          CORE
   Saved: base JFR -1.4 s prof html, -4.4 s first build (B sees the same frame, 2.7 CPU s).
   Risk: low if invalidated on resource change. Effort: small. Overlap: B.

10. Fragment pruning (-Dr2c.prune) with a scan of the IG's literal includes                        PUBLISHER
   Saved: measured about -0.8 to -1.3 s per prof rebuild (en+ru+uz 6.3-6.8 -> 5.5 s), -5.9 s first build.
     23,086 of 52,927 fragment groups skipped on a first build.
   Risk: medium. Template.wantGenerateFragment's whitelist (the upstream rapido pruning disabled by 0f53f940) has
     no non-fragment outputs (openapi, swagger, ...), so it drops those as well. Effort: small. Product decision.

11. Cheaper replay checks                                                                          PUBLISHER
   canReplay/fileHash re-hashes every output on disk (~0.7 s per rebuild); size + mtime from the journal would do
   (est -0.5 s). state.json stores each expansion 4x (123 of 192 MB); one copy per ValueSet by hash (est -1 s
   write/read, not measured).

12. Faster deflate for the big non-html zips                                                      PUBLISHER/CORE
   expansions.*.zip, definitions zips and validator.pack: ~3.7 s of native Deflater samples per build.
   Deflater.BEST_SPEED est -2 s; the zip bytes change but not the content. Moot for expansions if 4 holds.

Order I'd take them in: 2 (enabler, small), 5 (measured), 4 (small, half measured), 1 (largest render win, shares B's
code), 3 (largest wall win, with D), then 8, 9. Ideas 7 and 10 need an upstream decision first. 6 only after 2.
