# DRAFT 1: core #2856 v2
######################################################################

=== Title ===
Add TerminologyCache.scrub() to drop the cached answers for changed ValueSets and CodeSystems

=== Body ===
The tx cache keys a ValueSet that has a url and a version by url|version. An IG's ValueSets keep their version while they are edited, so the cache keeps answering with the old expansion and the old validate-code results. This keeps the url|version keys and adds a way for the caller, which knows what changed, to remove those answers.

### Cause

The cache key of a ValueSet with a url and version doesn't change when its content, or the content of what it includes, changes.

### Fix

`scrub(Collection<String> urls)` removes every entry whose request names one of the urls: expansions for any options and language, validate-code results against the ValueSet, and expansion, validate-code and subsumes results that name the url as a code system, an implicit value set (url?fhir_vs...) or an included ValueSet.
- It works on every named cache, in memory and in the cache files (saved straight away). That includes cache files whose cache isn't in memory, such as the ones removeCS drops for an IG's own CodeSystems.
- A url matches a whole url, with or without a |version. A url that only starts with it doesn't match.
- The expansion parameters (after "profile") are not looked at: they are the same for every request in a run, and they name code systems (system-version) that would match everything.
- A merge with the file on disk later in the session leaves out the disk's entries for the scrubbed urls, so a file without a nonce doesn't bring them back. Answers fetched after the scrub are kept.
- An expansion keyed by url|version doesn't name what it includes, so the caller passes the ValueSets that depend on what changed too. The publisher works that out from its dependency tracing (HL7/fhir-ig-publisher#<new>).

The same change is made in r5 and standalone. The #2827 handling of transient failures in store() is unchanged.

Tests: TerminologyCacheTests.Scrub in both modules: every kind of entry for a ValueSet and for a CodeSystem is removed in memory and on disk; prefix-similar urls, urls in the expansion parameters and in a display are kept; a quote before the url; a |version is ignored; a persistent entry whose key a transient entry took over; no resurrection through a merge, while a fresh answer survives it; a file whose cache removeCS dropped; a memory-only cache.

Numbers: the end-to-end proof is in HL7/fhir-ig-publisher#<new> (an edited ValueSet and the ValueSet that includes it now render the same expansion as a fresh build). Timings on uz.dhp.core: pending.

Replaces the content keys of the earlier version of this PR.

# DRAFT 2: publisher, new PR from fix/rapido-scrub-tx-cache
######################################################################

=== Title ===
Scrub the tx cache for the ValueSets and CodeSystems a build may have changed

=== Body ===
The tx cache keys a ValueSet by url|version, and an IG's ValueSets keep their version while they are edited. After an edit, rapido and -watch rebuilds keep using the old expansion and the old validate-code answers. They render the old expansion page and miss or report the wrong binding errors until the cache is deleted.

### Cause

Nothing removes a cached answer when the ValueSet, or something it depends on, changes without a version change.

### Fix

Before anything validates or expands against the cache, the publisher removes the cached answers for every ValueSet and CodeSystem that may have changed. It uses TerminologyCache.scrub() from hapifhir/org.hl7.fhir.core#<new>.
- A rapido build scrubs every VS and CS it rebuilds. Rebuilding is decided by the dependency closure from #1447, so the scrub covers a VS that includes or excludes a changed VS, a VS on a changed local CS (also through an implicit `cs?fhir_vs=...` value set), and a CS whose local supplement changed.
- Core sends every local supplement of a CS along with its expansions and validations, so a supplement is now an implied edge in RapidoDependencyAnalyser.closure().
- Unchanged VSs and CSs keep their entries.
- A url the IG defined in the last build and no longer does (deleted, or its url changed) is scrubbed too. The rapido state keeps the list, also after a build with tx failures.
- A build with nothing to compare against scrubs the url of every local VS and CS: a plain build, a rapido build with no state, and a build after a package change.
- The log shows how many entries were removed and how long it took.

Contains #1447's commits; review only the last four.

### Limits
- load() runs before the dependency check, so two things in it can still read an old answer for a changed VS: the snapshot step's required-binding check ("Binding X is not a subset of binding Y", only for a profile whose snapshot is regenerated), and test data factories. Fixing it means moving the dependency analysis before loadConformance1.
- An external CS that a local supplement extends (e.g. SNOMED CT) is scrubbed only in rapido builds where the supplement changed, not in every plain build, which would drop all SNOMED CT answers on every build. An external ValueSet on such a CS is not scrubbed.
- The list of last-build urls is saved only when a build gets that far. A url changed to Y, a crash, then a change away from Y leaves Y unscrubbed.
- A dependency package that changes without changing its version is not scrubbed.

Tests: RapidoTxCacheScrubTest (8: VS, CS and supplement edits scrub them and their dependants, nothing changed keeps all, a plain build scrubs all local urls, renamed and deleted urls, deleted after a build with tx failures); RapidoDependencyAnalyserTest (supplement edges, a VS on an implicit value set of a local CS). Each new test was checked by breaking the code it covers.

Proof (small FSH IG, VS B includes VS A, VS A edited without a version bump, -rapido -watch, same seeded tx cache):

| build | 112144000 in VS A | expansion of VS A | expansion of VS B |
|---|---|---|---|
| master, after removing it | no | still listed (stale) | still listed (stale) |
| this PR, after removing it | no | gone | gone |
| fresh build, empty cache | no | gone | gone |

The expansions with this PR are identical to the fresh build's, and QA counts are the same in all three. Timings on uz.dhp.core: pending (needs a machine that fits a 10 GB publisher plus Jekyll).

=== Body (replaces the current one) ===
Since #1363 the expansion page of each ValueSet is generated without the tx cache, so every build sends all of them to the tx server again.

### Cause

#1363 replaced `ExpansionOptions.cacheNoHeirarchy()` with `new ExpansionOptions().withHierarchical(true)` to get the hierarchy back. `cacheOk` defaults to false, so the cache was dropped too.

### Fix

- Add `withCacheOk(true)`.
- The page code clears the compose and text of the ValueSet it renders, which is now the cached object, so it renders from a copy.

Depends on #<scrub PR> and hapifhir/org.hl7.fhir.core#<new>: every VS a build may have changed has its cache entries removed first, so an edited ValueSet doesn't show its old expansion. Without them, this change makes that stale page visible (see the proof below). The pages of unchanged ValueSets come from the cache in rapido and -watch rebuilds; a plain or complete build scrubs the IG's own ValueSets anyway.

No new tests: one call site, checked by editing a ValueSet without a version bump in a -watch session.

Proof (small FSH IG, VS B includes VS A, VS A edited without a version bump, -rapido -watch, same seeded tx cache):

|---|---|---|---|
| master (with this commit), after removing it | no | still listed (stale) | still listed (stale) |
| with the scrub PRs, after removing it | no | gone | gone |
| fresh build, empty cache | no | gone | gone |

The expansions with the scrub PRs are identical to the fresh build's, and QA counts are the same in all three. Timings on uz.dhp.core: pending (needs a machine that fits a 10 GB publisher plus Jekyll).
