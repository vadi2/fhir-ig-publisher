## What was checked (empirically)

Each IG was built twice from the same sources: a `-rapido` differential rebuild after an edit to IG entry text only, and a fresh full build without `-rapido`. Both outputs were compared with a normalised diff (UUIDs, timestamps and paths stripped), plus a grep for the new and old text.

- **ChitSR/sample-ig (XML IG, AU template).**
  - The edit renamed the example entry and changed its description, and changed the profile entry's description.
  - The rebuild was differential, not complete.
  - The new text appears in exactly the same files in both builds, and the old text appears nowhere. Those files are:
    - `artifacts-table-data.js` (the artifacts page)
    - `toc.html`
    - the IG resource pages and formats
    - `examples.html`
    - `StructureDefinition-myobservation-examples.html`
    - the example's own pages
  - Outputs are identical apart from qa/timing files.
- **HL7/fhir-consent-management (FSH, fast template).**
  - Adding a Title made SUSHI reorder `definition.resource`. That correctly gave a complete build ("changed: ig").
  - An edit that kept the order (instance Title/Description) gave a differential build: 62 of 106 files rendered.
  - Output equals the full build except for the order of the "used by" column in `valueset-ref-all-list` and `codesystem-ref-all-list` (csv/json). That comes from a `HashSet<Resource>`, and two full builds differ the same way. It is not Rapido and not this PR.
- **Why the IG-wide pages are current.**
  - The IG file is always processed.
  - The template builds the artifacts table from the IG every build.
  - `generateDataFile` (`resources.json`), `pages.json`/`toc.xml` and the summary/list fragments run every build, outside replay.
  - Pages that list an entry by name elsewhere (a profile's examples) are reached through the dependency edges the PR adds.

Nothing was stale, so there is no production fix.
