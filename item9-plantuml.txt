THE BUG
- In -rapido, a complete build that follows a differential build deletes the PlantUML svgs. Jekyll then fails:
  "Liquid Exception: Could not locate the included file 'practitioner-certificate-sequence.svg' in _includes".
- Triggers: in -watch, the first build after local midnight ("Complete Build (changed: date)"; with #1461 it also
  logs "Complete Build (the day changed since the last build)"). Also any other complete build after a
  differential one: template, jar or command line changed, and so on.
- On uz.dhp.core (9 diagrams in input/images-source/*.plantuml).

CAUSE
1. The template's ant target onGenerate.artifactList lists ${temp}/_includes/*.svg as pages BEFORE onGenerate.plantUml
   writes them. So from the 2nd build of a temp folder on, the svgs are FetchedFiles (loaded by
   PublisherGenerator.templateBeforeGenerate -> loadPrePage). RapidoOutputs records them as those pages' outputs
   (_includes/X.svg and _includes/{en,ru,uz}/X.svg) in <vsCache>/.build-outputs.json.
2. A complete build clears the temp folder first (Publisher.checkDependencies -> PublisherIGLoader.clearTempFolder).
   The template then lists no svgs, and plantUml writes them again as no page's output.
3. #1447 b5d73d56 changed RapidoOutputs.update() to read the old record even when every file is generated. The svgs
   are reported "gone", and the gone loop in PublisherGenerator (~line 465 on #1447:
   `for (String gone : change.getGone()) if (!isValidFile(gone)) delete`) removes them before Jekyll runs.
   On master, update() only read the record for partial builds, so master doesn't have the bug.

THE FIX (d1f9c352, ~12 lines of main code)
- RapidoOutputs.forget(): Files.deleteIfExists(record). PublisherIGLoader.clearTempFolder() calls it at the end:
  the record describes the temp folder, so it goes when the folder is cleared.
- In the complete build, update() has no "before": nothing is gone and a fresh record is written, so the next build
  is differential again. (Complete builds always have changeList == fileList, so update() doesn't return null.)
- A failed delete throws and fails the build, on purpose: carrying on would bring the bug back silently. The next
  build is then "Complete Build (after failure)", which retries.
- The RapidoTracker state is already in temp/_rapido, so it goes with the temp folder. Only the outputs record lived
  outside it.

Title: Rapido: forget the outputs record when the temp folder is cleared

In `-rapido`, a complete build that comes after a differential one deletes the PlantUML svgs, and Jekyll fails with "Could not locate the included file 'X.svg'". In `-watch`, the first build after midnight hits it ("Complete Build (changed: date)"), and so does any other complete build (template, jar, command line changed).

### Cause

- The template's `onGenerate.artifactList` lists `temp/_includes/*.svg` as pages before `onGenerate.plantUml` writes them. So from the second build on, the svgs are pages, and `RapidoOutputs` records them as those pages' outputs (`.build-outputs.json` in the tx cache folder).
- A complete build clears the temp folder first, so the template lists no svgs, and `plantUml` writes them again as no page's output.
- #1447 made `RapidoOutputs.update()` diff against the old record even when every file is generated. The svgs come out as gone, and the clean-up deletes them before Jekyll runs. Master only reads the record in partial builds, so master isn't affected.

### Fix

- The record describes the temp folder, so `clearTempFolder()` now deletes it (`RapidoOutputs.forget()`). The complete build has no old record to diff against. It removes nothing and writes a new record, so the next build is differential again.
- If the delete fails, the build fails. Carrying on would bring the bug back.

Adds `PublisherRapidoWatchTest.aCompleteBuildDoesntRemoveWhatTheTemplateScriptsWrote` (day change, through `checkDependencies`) and `RapidoOutputsTest.afterTheTempFolderIsClearedNothingIsGone`. Both fail without the fix, and the existing tests pass.

Checked on uz.dhp.core (9 PlantUML diagrams), `-rapido -watch`. The JVM time zone was set so that local midnight fell between the second and third build (it isn't part of Rapido's command hash). The run: first build, instance edit (differential), then after midnight a page edit and one more page edit.

| After midnight | #1447 stack | with the fix |
|---|---|---|
| Build | Complete (changed: date) | Complete (changed: date) |
| svgs in temp/_includes | 0 | 9 |
| Jekyll | fails: practitioner-certificate-sequence.svg | ok |
| Next page edit | Complete Build (after failure) | Page Rebuild |

Plain `-rapido` on #1447 alone, with a fresh build, then a page edit (differential), then the next day: the third build is "Complete Build (changed: date)", leaves 0 svgs and Jekyll fails the same way. TODO: the same three runs with the fix, and on master.

GOTCHAS
- The bug needs a DIFFERENTIAL build before the complete one: the svgs only become pages, and get recorded, when the
  template's artifactList finds them from the last build. A fresh first build is always safe.
- Don't trust the output/ file list in watch mode after a failed build: #1458's staging keeps the old output, so
  output/en/workflow-lab.html still had the diagram. Check temp/pages/_includes and the Jekyll lines.
- -Duser.timezone doesn't change Rapido's "command" hash; the program args do. Keep the args identical between runs
  that should be compared.
- #1461 logs two complete-build lines after midnight (PageRebuild's "the day changed since the last build", then
  RapidoTracker's "changed: date"); #1447 alone logs only the second.
- When cherry-picking onto other rapido branches, PublisherRapidoWatchTest conflicts (its build() helper differs).
  Port the test rather than union-merging.
- uz.dhp.core needs ~10 GB of heap and ~7.6 GB of disk per bench copy (output + temp), so clean them between runs.
