2. WHAT IT DOES AND WHY
-----------------------
Problem: ImplementationGuideValidator.checkDependency (org.hl7.fhir.validation, instance/type) runs for every
dependsOn whenever the IG resource is validated. Each call builds a NEW FilesystemPackageCacheManager (so a new
CIBuildClient, which downloads build.fhir.org/ig/qas.json, ~1.7 MB, again; its own 1 h interval never applies),
calls pcm.getPackageId(uri) (local cache, then catalog ?pkgcanonical= search on packages2.fhir.org/packages.fhir.org,
then the CI list), getPackageUrl, and for IGs marked for publication PackageClient.getVersions + getLatestVersion.
Nothing is kept between calls or builds. The test IG uz.dhp.core has 3 dependsOn (hl7.terminology.r5 7.5.0,
fhir.dicom 2025.2.20250411, hl7.fhir.uv.extensions.r5 5.4.0); the registries answer [] to pkgcanonical= for all
three, so each falls through to qas.json.

Change:
- New org.hl7.fhir.utilities.npm.RegistryAnswerCache: url -> parsed answer, with a ttl, ConcurrentHashMap, injectable
  clock (package-private ctor for tests). get(key, fetcher) and get(key, fetcher, keep): a kept answer younger than
  the ttl is returned; otherwise fetch, and keep only if keep.test(value).
- PackageClient(PackageServer, @Nullable RegistryAnswerCache): search() and getVersions() go through it. Processing
  loops extracted to readCatalog/readVersions (unchanged logic); the keep predicate runs them on a scratch list and
  rejects on RuntimeException (canRead). getVersions also requires a "versions" object (registries answer an unknown
  package with 404, which throws and isn't kept).
- CIBuildClient: withAnswers(cache) (package-private); updateFromCIServer fetches qas.json via the cache keyed
  rootUrl + "/ig/qas.json", keep = canRead (readBuilds doesn't throw). Loop extracted to readBuilds, unchanged.
- FilesystemPackageCacheManager.Builder: @With registryAnswerCache field (null = off, master behaviour); build() wires
  it into the CIBuildClient and a client factory; both getLatestVersion overloads now use newPackageClient(server)
  (new protected BasePackageCacheManager.newPackageClient) so they go through the factory.
- ImplementationGuideValidator: private static final RegistryAnswerCache REGISTRY_ANSWERS (1 h, same as
  CIBuildClient's interval), passed to the Builder and to PackageClient(primaryServer, ...).
- Semantics (follows #2827's rule for tx failures): failures (IOException, error status, parse errors, wrong top-level
  type) throw and are never kept; bodies that parse but can't be read are returned as on master but not kept; an
  empty catalog [] IS an answer and is kept; the cache holds raw JSON, so exactMatch / milestones-only filtering by
  one caller doesn't leak to the next.
- Only the validation module has the validator, so no r5/standalone duplication is needed. No existing core cache fit
  (CIBuildClient's interval is per instance; the package cache is for package content, not registry queries).

Accepted by design (say so in the PR text, don't re-fix):
  - the static cache is shared by every validator in the process for up to 1 h (a newly published dependency version,
    and wildcard resolution in loadPackage, can lag up to 1 h);
  - memory held by the parsed qas.json (~1.7 MB JSON);
  - malformed-but-parseable upstream data (qas.json entry without url, version entry without version) is kept like any
    other answer for 1 h; master fails on it too, it just re-asks each build. Live qas.json has no such entries.
  - with a cache set, build() wraps the default CIBuildClient via withAnswers (a custom subclass would be replaced);
    keys are urls only (two servers with the same url but different auth would share answers). Both theoretical.

8. DRAFT (current text)
-----------------------
Title: Keep registry answers for IG dependency checks for an hour
Branch: perf/ig-validator-registry-cache (local, not pushed), base master 4ea8d00521, commits 3b45de010d 984e4a97b8 91100d3df1 71de93fde6

In an IG Publisher watch session, every build that validates the ImplementationGuide resource (a complete build, or any rebuild after an edit that changes the IG resource, such as a page title) asks the package registries and build.fhir.org the same questions again for each `dependsOn`. On uz.dhp.core (3 dependencies) that costs 2.5-3.1 s of network time in each such build on master (NREQ requests), and the first build asks the same questions once per dependency.

### Cause

- `ImplementationGuideValidator.checkDependency` builds a new `FilesystemPackageCacheManager` for every dependency, so it also gets a new `CIBuildClient`, whose 1 h interval never applies: each one downloads `qas.json` again.
- It then searches the catalog by canonical (packages2 and packages), lists the package's versions, and for IGs marked for publication asks for the latest version. None of it is kept between calls.

### Fix

- New `RegistryAnswerCache` in utilities/npm: answers kept by url for a ttl. `PackageClient` (catalog search, version list) and `CIBuildClient` (`qas.json`) use it when given one. `FilesystemPackageCacheManager.Builder.withRegistryAnswerCache` passes it to both, and `getLatestVersion` now goes through the client factory so it uses it too.
- Only answers are kept. A request that fails (error status, timeout, no network, a body that doesn't parse) throws as before and the next caller asks again, as #2827 does for tx failures. A body that parses but can't be read (a version list without versions, entries that can't be read) is returned as on master but not kept. A catalog search that finds nothing is an answer; an unknown package is a 404, so it is asked again.
- The cache holds the registry's JSON, not the filtered lists, so `exactMatch` or milestones-only calls don't change what the next caller gets.
- Nothing changes unless a cache is given. Only `ImplementationGuideValidator` opts in, with a static cache and a 1 h ttl, the same as `CIBuildClient`'s interval. So for up to an hour a validator in the same process doesn't see a newly published version of a dependency.
- The validator is only in the validation module, so there is no r5/standalone copy to change.

Adds 21 tests in `RegistryAnswerCacheTests` against a fake registry (MockWebServer, no network), each checked to fail with its part of the change reverted; existing npm tests pass.

9. GOTCHAS
----------
- Instance edits don't validate the IG resource on current publisher master (see 5); the round-2 "-3 s on every
  rebuild" came from an older publisher stack. Measure with Title edits (complete builds) and say so in the PR.
- `jfr print` defaults to --stack-depth 5: without --stack-depth 256 no event shows ImplementationGuideValidator.
- The HTTP client retries once, and CIBuildClient retries once after 1 s: failure tests must keep the fake server down
  for the whole call (flag), not fail a single request, and assert relative counts.
- CIBuildClient stamps its query time even on failure (#2238, deliberate) - unchanged. Throwing inside the fetcher for
  an unreadable qas.json left ciBuildInfo null and NPE'd in getPackageUrl, unlike master: hence the keep predicate
  (return the value as master does, just don't keep it).
- Lombok @With on the Builder needs the all-args constructor in field order (5 args incl. registryAnswerCache), and the
  hand-written withXxxCacheFolder methods must pass the cache on.
- PackageClient.search swallows IOException into an empty list and getVersions swallows Exception (pre-existing,
  unchanged). search still lets a RuntimeException from a bad date propagate, as on master.
- Offline Maven runs of org.hl7.fhir.utilities need -Danimal.sniffer.skip=true to avoid unrelated sniffer errors.
- Each uz.dhp.core watch session writes ~7 GB to output/ + temp/ and wants a 10 GB heap: check free disk and RAM before
  each session and delete output/temp between sessions.
