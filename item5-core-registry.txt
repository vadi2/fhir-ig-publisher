Title: Keep registry answers for IG dependency checks for an hour

In an IG Publisher watch session, every build that validates the ImplementationGuide resource (a complete build, or any rebuild after an edit that changes the IG resource, such as a page title) asks the package registries and build.fhir.org the same questions again for each `dependsOn`. On uz.dhp.core (3 dependencies) that costs 2.5-3.1 s of network time in each such build on master, and the first build asks the same questions once per dependency.

### Cause

- `ImplementationGuideValidator.checkDependency` builds a new `FilesystemPackageCacheManager` for every dependency, so it also gets a new `CIBuildClient`, whose 1 h interval never applies: each one downloads `qas.json` again.
- It then searches the catalog by canonical (packages2 and packages), lists the package's versions, and for IGs marked for publication asks for the latest version. None of it is kept between calls.

### Fix

- New `RegistryAnswerCache` in utilities/npm: answers kept by url for a ttl. `PackageClient` (catalog search, version list) and `CIBuildClient` (`qas.json`) use it when given one. `FilesystemPackageCacheManager.Builder.withRegistryAnswerCache` passes it to both, and `getLatestVersion` now goes through the client factory so it uses it too.
- Only answers are kept. A request that fails (error status, timeout, no network, a body that doesn't parse) throws as before and the next caller asks again, as #2827 does for tx failures. A body that parses but can't be read (a version list without versions, entries that can't be read) is returned as on master but not kept. A catalog search that finds nothing is an answer; an unknown package is a 404, so it is asked again.
- The cache holds the registry's JSON, not the filtered lists, so `exactMatch` or milestones-only calls don't change what the next caller gets.
- Nothing changes unless a cache is given. Only `ImplementationGuideValidator` opts in, with a static cache and a 1 h ttl, the same as `CIBuildClient`'s interval. So for up to an hour a validator in the same process doesn't see a newly published version of a dependency.
- The validator is only in the validation module, so there is no r5/standalone copy to change.

Adds 21 tests in `RegistryAnswerCacheTests` against a fake registry (MockWebServer, no network), each checked to fail with its part of the change reverted; existing utilities and validation tests pass (validation failures are the same as on master).
